## 1. 一句话结论

**补丁 7B（KV_PASSTHRU，在途砖 pin 名单）把"砖何时可驱逐/何时归还槽位"的时机改了，导致 CPU 镜像池被在途砖占满、`prepare_store` 长时间返回 None（`cannot store chunks` 连续 10 分钟 2760 条）；在这个满负荷边缘状态下，下一次"从盘读回前缀"的块数越过了 vLLM 自己 for 滑窗组的预算断言 `num_pending_gpu_blocks <= sliding_window_size_in_chunks * blocks_per_chunk + 1`，EngineCore 直接崩。**

这是**死路清单里那个断言第一次在"已宣称全绿"的配置上、于长时间真实负载中复发**——它不是启动期问题，是运行期账本慢性失衡的结果。

## 4. 崩的那条断言到底在检查什么

`offloading/scheduler.py:1147-1156`（stock 代码）：

```python
assert num_locally_computed_tokens % tokens_per_block == 0
num_pending_gpu_blocks = num_gpu_blocks - load_start_gpu_block_idx

if group_config.sliding_window_size_in_chunks is not None:
    assert (
        num_pending_gpu_blocks
        <= group_config.sliding_window_size_in_chunks
        * self.config.blocks_per_chunk
        + 1
    )
```

- `load_start_gpu_block_idx` = 从"已算好的边界"往后扫，找**第一个还没内容（block_hash is None）的新鲜 GPU 块**，也就是"这次要从外存搬回来、得占用 GPU 块"的起点。
- `num_pending_gpu_blocks` = 这一段**需要从盘/CPU 读回并占用的 GPU 块数**。
- 对滑动窗口组（sliding window）来说，这个数**天生有上限**——滑窗只保留最近 N 个 chunk 的 KV，所以"要补的块"不可能超过 `窗口 chunk 数 × 每 chunk 块数 + 1`。这是上游拿它当**不变量**用的：谁超过这个数，就说明**块账本对不上了**。

崩溃即宣告：**这次读回要占的 GPU 块数，比一个滑窗组理论上最多能拥有的块数还多。** 换句话说，`num_locally_computed_tokens`（本地已算/已命中的 token 数）与 `num_gpu_blocks`（这次分配到的 GPU 块数）之间的关系被搞坏了——上游认为"这不可能发生"，所以只写了 assert 没写恢复。

## 5. 根因分析：7B 把驱逐时机改了，账本失衡在满池时被引爆

补丁 7B 的机制（见 `patches/0004`）：
- 砖一进 CPU 池就 `pt_pin()`：从可驱逐队列（evictable）里摘出去，进 `_pt_pinned` 名单，**LRU 永远不动它们**。
- 只有盘上确认有货（`pt_unpin_on_disk`）才退回普通 LRU。
- `complete_load` 里还加了 `if key in self._pt_pinned: continue`（不归还可驱逐计数）。

这套设计的初衷是对的（"内存只住镜像，绝不被在途过路货挤掉"），但副作用是：

1. **在途砖既不能被驱逐、又不算可驱逐量，却实打实占着 `chunk_id` 槽位。** 只要"写盘速度 < 进池速度"（此盘单流 55-93MB/s，正是最窄处），`_pt_pinned` 名单就会持续变长，把可驱逐砖全挤出去，直到**一个都驱逐不动** → `prepare_store` 返回 None → 就是那 2760 条 `cannot store chunks`。11-26 那次我们把这条 WARNING 归因为"RAM 中转层堵"，改 12G→16G；这次是**同一个症状换了内因**：不是 RAM 总量不够，是 **7B 把可用槽位锁在名单里出不来**。
2. 长期"钉住不放 + 拒绝驱逐"的砖，会让 scheduler 侧的 `req_status.num_locally_computed_tokens` 与实际块状态出现时间差。当这条链路上的请求在 20:38-20:41 极端拥塞、又被抢占/重算（`kv_load_failure_policy=recompute` 会把命中数退回 0 重算）反复搅动时，`update_state_after_alloc` 读到的组合就越过了滑窗预算。
3. 崩溃点之前一行是 `self.connector.update_state_after_alloc(...)`，**由 schedule() 直接调用**——也就是崩溃发生在"分配完 GPU 块、连接器要登记这次要读回什么"的那一刻，正是 7B 改动过生命周期的那批块的交接点。

一句话：**补丁 7B 用"不驱逐"换"镜像保护"，把 CPU 池推进了"全员钉住"的稳态，边缘状态下引爆了上游的滑窗块数不变量。**

## 6. 为什么"11-27 实测全绿"没抓到它

当天 16:40 那轮测试确实全绿（见 README / 技能记录），但四条用例都是**单会话推进**：
- 256K 冷建（看盘速）→ 下灶 → 切回 A 看镜像命中 → md5 一致 → 无 AssertionError。

测试里没有出现的是：
- **多个请求同时在途 + 长请求 + 盘速跟不住 + kv-cleaner 正好在删** 的拥塞叠加态；
- 观测时长只有几十分钟，而本次故障是**累积 5 小时**才越过阈值（`cannot store` 的峰值 20:38/20:41 才是信号，测试时段根本没到这个量）。

所以"绿"是真的绿，绿的是"不崩在启动/首测"（比补丁 4/5/6 强），**不是"运行期账本守恒"**。教训：**7B 的验收必须加"长时间多请求拥塞压测 + `cannot store` 速率红线"**，只看首轮不崩不够。

## 7. 崩溃之后的连锁事实（顺带记全，免得下次重查）

1. **自动重启全部失败**：`start-dflash2.sh` 有 `DFLASH_BOOT_ATTEMPTS=3` 重试；20:43、20:44、20:46、20:47、20:48 共 5 次尝试，最后两次报
   `ValueError: Free memory ... less than ...`（死路清单 #2 的老坑：失败启动残留显存，`wait_gpu_free` 这次没等够/没救回），20:48 后放弃。**服务从 20:41 起一直没人管。**
2. **没有任何通知发出去。** cron 任务 `GPU dual-card watchdog`（每 3 分钟）整晚都在正常跑、状态 ok，但它的判据是"`nvidia-smi` 数够 2 张卡就静默"——**卡还在，进程死了它看不见**。当晚日志全是 `silent (empty output)`。最近一条真正推到飞书的 vLLM 消息还是早上 08:18 `gpu-warm-watch` 的"vLLM 已就绪"。**看门狗缺一条"服务存活"的腿，这是监控漏洞不是运气问题。**
3. `:8001` 网关（pid 13495）活得好好的，对着死上游一直回 502，journal 里刷 `model-alias-proxy.py` 的 traceback——客户端只看到"模型连不上"，看不出服务器内部已崩。
